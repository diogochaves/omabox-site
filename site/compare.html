ai-jail decides what the agent can touch. omabox decides where it draws.

Two questions, two tools.

ai-jail, by Fabio Akita (AkitaOnRails), is the sandbox we point people to. It runs an agent inside bubblewrap, Landlock and seccomp on Linux, and sandbox-exec on macOS. It does carefully the one thing omabox doesn't do: limit what the agent can read, write and reach.

ai-jail answers: what can it touch?

A fence around the agent

  • Your project read-write at its real path, /usr read-only
  • A fresh home: no ~/.ssh, ~/.aws, ~/.gnupg or browser profiles
  • The environment cut to an allowlist, so your tokens stay in your shell
  • The network cut to what you allow: since ai-jail 2.8, a bare ai-jail claude reaches its model's API and nothing else
aijail.io ↗github.com/akitaonrails/ai-jail ↗

omabox answers: where does it draw?

A desktop of its own

  • Its own screen, pointer and keyboard
  • Its own session bus, tray, notifications and keyring
  • Your cursor, focus and workspaces untouched
  • Not a security boundary: that part is ai-jail's
How a box keeps off your desktop →

Two recipes, both tested.

Neither needs a change to ai-jail.

A jailed app, drawn in a box

A contributor's branch, an app you just downloaded: run it in ai-jail, with the box's screen as its only display. ai-jail keeps it out of your home, keys and network; its window opens in the box, where omabox shot and peek see it.

$ omabox up
$ eval "$(omabox env)"   # Wayland clients now draw in the box
$ ai-jail --gpu --rw-map "$WAYLAND_DISPLAY" \
    --env WAYLAND_DISPLAY -- ./build/app

Tested with ai-jail 2.8.1 and omabox 0.5.2 on Linux, and before that with ai-jail 2.2.1 and 2.6.2.

A jailed agent, driving boxes of its own

A jail can't start a box itself (its seccomp filter refuses new namespaces), so its omabox hands each command to a broker outside. Turn it on once, add the lines it prints, then start your agent in ai-jail as usual.

$ omabox broker on   # prints the lines to add to ~/.ai-jail
$ ai-jail claude

Tested with ai-jail 2.8.1 and omabox 0.5.2 on Linux, and before that with ai-jail 2.2.1 and 2.6.2. omabox broker off turns it off.

What a jailed agent can and can't do.

Driving a box is running code in it, so the broker is what keeps a box from being a way out of the jail. It reads the jail's limits from the jail's own command line, which nothing inside can change, and gives each box no more than the jail has.

In the jail, as outside

  • up, run, shot, keys, click, wait and the rest
  • record: the video, its marks and captions land in the jail's project, written by the agent's own omabox
  • ports, for its own boxes: a port held by anything else is said to be taken, without naming who holds it
  • git in a box started from a worktree

Not from a jail

  • omabox host, which runs on your real desktop
  • peek and interactive boxes, which open on your screen
  • The guard, saves, clip and config changes; which host ports you protect isn't shown to it
  • Boxes you or another jail started
Its network

None when the jail has none: its boxes start --net isolated. With ai-jail 2.8's default, the agent reaches its model's API and its boxes still get no network.

Its project

Only the jail's own project goes into a box, and what the jail hides in it (its .ai-jail included) stays hidden there too.

Its boxes

Only the boxes that jail started, and they go down when the jail exits.

Upgrading from 0.x to 1.0? Restart agents running in ai-jail: a jail started before the upgrade keeps its old relay. And omabox is still not a security boundary. A box keeps an agent's windows off your desktop, not code written to escape: for code you don't trust, use ai-jail, or a VM. The rule for jailed agents and the test behind it are S9 in SECURITY.md.
